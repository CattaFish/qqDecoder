# qqDecoder

基于 GitHub Actions 实现的腾讯 QQ 安卓版自动化监控、反编译、增量 Diff 追踪与发布工作流。

项目支持多版本队列排队、硬件自适应调优与代码变动精准提取，每次更新会自动将完整的 Java 源码包及版本差异补丁发布至 GitHub Releases。

## 核心特性

- 多版本队列与自动接力：支持应对单日多版本发布的场景。工作流会按时间正序构建待处理队列，遵循先进先出（FIFO）原则单次处理最早的未完成版本，发布成功后自动触发下一次运行，直至清空积压队列。
- 动态自适应算力调度：运行期自动探测虚拟机各分区（根分区 `/` 与临时分区 `/mnt`）的可用容量，在保留 18GB 物理磁盘作为绝对安全垫的前提下，动态开辟最高 64GB Swap 虚拟内存，并联动分配最高 48GB 的 JVM 堆内存（`-Xmx`），彻底杜绝内存溢出（OOM）与磁盘写满故障。
- 智能增量 Diff 引擎：专为数十万反编译小文件场景设计。使用内置轻量脚本基于文件元数据与 Hash 预检，绕过 Git 极其耗时的重命名相似度计算，秒级过滤混淆变动，精准提取核心业务（如 QQNT）同名类的行级修改，并打包输出高价值的 `diff.patch.zip`。
- 事务性状态持久化：版本记录文件 `latest_version.txt` 仅在产物成功发布到 Release 后才执行提交与推送。若反编译中途被手动终止或异常崩溃，远程记录保持不变，下次运行将自动重试失败版本，避免漏包。

## 工作原理

1. 版本检测与增量排队
   定时拉取 Telegram 频道的免登录 Web 预览页（单次约 20 条消息），按时间正序收集所有包含官方 APK 直链的消息，比对本地记录的基准版本，构建待处理列表。
2. 磁盘瘦身与优选分区
   执行虚拟机深度瘦身（清理预装的 dotnet、ghc、boost 等大型套件），动态比对根目录与临时挂载盘的可用空间，择优指定主力存储驱动器。
3. 算力动态计算
   根据优选分区的可用容量，减去 18GB 预留空间后计算 Swap 大小（区间限制在 16GB 至 64GB 之间）。随后根据总可用内存池（RAM + Swap）计算分配给 JADX 的最大堆内存。
4. 反编译与容错处理
   提取 APK 中的全部 `classes*.dex`，运行 JADX 反编译为 Java 源码。配置有局部导出过滤规则（支持仅反编译核心包），并对非致命的局部损坏类提供退出码兼容机制。
5. 智能源码 Diff
   通过 GitHub CLI 自动拉取上一版本的产物包并解压，采用集合与 Hash 比对统计新增、删除与修改的文件清单，针对实质修改的类生成 Unified Diff 补丁并压缩封包。
6. 资产发布
   使用 GitHub CLI 创建对应版本的 Release，上传源码压缩包、Diff 补丁包，并以 Markdown 折叠块形式附加文件变动统计概览。
7. 状态回写与接力唤醒
   Release 发布成功后，将当前已处理的直链写入 `latest_version.txt` 并推送到仓库主分支。若检测到队列中仍有待处理版本，自动调用 GitHub API 触发自身工作流执行下一轮处理。

## 配置与部署

如需在个人仓库中运行此项目，请按以下步骤配置：

### 1. 开启工作流写入权限
工作流需要自动提交版本记录、发布 Release 并支持自动触发后续任务，必须为 `GITHUB_TOKEN` 授予写入权限：
1. 打开 GitHub 仓库，进入 **Settings**。
2. 在左侧菜单中进入 **Actions** -> **General**。
3. 滚动到底部找到 **Workflow permissions**，选择 **Read and write permissions**。
4. 勾选下方 **Allow GitHub Actions to create and approve pull requests**，点击 **Save** 保存。

### 2. 运行工作流
- 定时自动检测：默认配置每天北京时间早上 8:00（UTC 0:00）运行检测。仅在检测到有未处理的新版本时才会继续执行后续反编译。
- 手动按需触发：在仓库的 **Actions** 页面，选择 **Auto Decompile QQ APK** 并点击 **Run workflow**：
  - `decompile_all`：是否完整反编译整个 APK（耗时与产物体积显著增加）。
  - `decompile_mobileqq`：局部反编译时是否包含 `com.tencent.mobileqq`。
  - `decompile_qqnt`：局部反编译时是否包含 `com.tencent.qqnt`。

## 性能与架构说明

### 针对反编译场景的 Diff 优化
在面对十万级混淆 Java 源码时，传统的 `git diff --no-index` 会因为混淆导致的类名变化触发代价极高的重命名相似度匹配（时间复杂度高达 O(N*M)），导致 CPU 卡死，并生成动辄数 GB、充斥垃圾数据的无意义补丁。
本项目通过 Python 预筛选：
1. 先比对文件路径集合，确定增删文件；
2. 对同名文件优先比对文件尺寸，尺寸一致再计算 MD5；
3. 仅对同名且内容发生变化的类执行行级差异生成。
全流程在 1 分钟内即可完成数十万文件的比对，产出的补丁体积通常仅数兆字节，且具备实际可读性。

### 自适应虚拟内存设计
GitHub Actions 分配给各运行环境的物理机器规格存在随机性（部分为 150GB 单盘机，部分为根目录 30GB、临时目录 70GB 的分盘机）。硬编码 Swap 大小容易在分盘机上触发磁盘耗尽。
自适应算法根据当前物理盘容量动态伸缩，确保在单盘大盘机上跑满 64GB 虚拟内存以提高反编译吞吐量，在小盘或分盘机上收缩至安全阈值，兼顾性能与运行稳定性。
