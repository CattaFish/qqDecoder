# qqDecoder

基于 GitHub Actions 实现的腾讯 QQ 全平台自动化监控、多渠道逆向感知、客户端识别码（SubID）提取、自动化反编译、增量 Diff 追踪与发布工作流。

项目支持全网多厂商应用市场无缝轮询、静默换包精准捕获、硬件自适应调优与字节码变动追踪，每次检测到官方或渠道更新时，会自动提取客户端元数据并生成增量数据库，针对官方正式包自动将完整的 Java 源码包及版本差异补丁发布至 GitHub Releases。

## 核心特性

- 全渠道应用商店感知矩阵：全面覆盖 Telegram 官方频道及国内主流应用市场，深度逆向各厂商私有协议与签名算法，实现全自动化无缝轮询：
  - 官方渠道：Telegram 更新频道（支持 Markdown 富文本链接与无前缀版本解析）
  - 厂商应用市场：小米（APM 私有协议签名）、OPPO / 一加 / realme（动态双 Salt 鉴权与 302 调度穿透）、vivo（Package 结构化开放接口）、华为（HiSpace 客户端报文协议）、荣耀（独立云端 HmacSHA256 签名体系）、三星（Galaxy Store 国区 ODC XML 协议）
  - 第三方应用分发：腾讯应用宝（微下载与直连 CDN 调度）、豌豆荚（PP助手）、应用汇（客户端原生移动 API）
- 版本与直链双重联合感知机制：针对应用市场“同版本静默换包”（即版本号未变但内部打包修复）的痛点，采用“版本语义比较 + 下载直链变动”双重校验机制。仅在线上版本严格递增或下载直链变更时触发任务，天然免疫应用市场灰度撤包回滚干扰，杜绝漏包与重复下载。
- SubID 深度提取与不可变历史账本：安装包下载后自动调用 AAPT 导出 `AndroidManifest.xml` 二进制属性，精准抽取手机端（`AppSetting_params`）与平板端（`AppSetting_params_pad`）的 9 位识别码（SubID），严格遵循“只增不减（Append-Only）”原则追加写入主数据库 `data/qq_subid_map.json`，完整记录历史换包演进轨迹。
- 运行时轻量字典自动编译：每次数据库发生增量变动时，底层编译引擎自动将多渠道实体编译为面向运行期的结构化字典 `data/subid.json`，自动完成多渠道同名 SubID 的交叉聚合，供下游补丁引擎毫秒级调阅。
- 多版本队列与自动接力：支持应对单日多版本发布的场景。工作流按时间正序构建待处理队列，遵循先进先出（FIFO）原则单次处理最早的未完成版本，发布成功后自动触发下一次运行，直至清空积压队列。
- 动态自适应算力调度：运行期自动探测虚拟机各分区（根分区 `/` 与临时分区 `/mnt`）的可用容量，在保留 18GB 物理磁盘作为绝对安全垫的前提下，动态开辟最高 64GB Swap 虚拟内存，联动分配最高 48GB 的 JVM 堆内存（`-Xmx`），彻底杜绝反编译大包时的内存溢出（OOM）与磁盘写满故障。
- 智能增量 Diff 引擎：专为数十万反编译小文件场景设计。使用内置轻量脚本基于文件元数据与 Hash 预检，绕过 Git 极其耗时的重命名相似度计算，秒级过滤混淆变动，精准提取核心业务同名类的行级修改，并打包输出高价值的 `diff.patch.zip`。
- 事务性状态持久化：版本与直链记录仅在产物成功落盘并推送后才更新。若流程中途异常中断，远程记录保持不变，下次运行将自动重试失败任务，避免漏包。

## 工作原理

1. 多源异步监控与双重比对
   监控总线按计划定时并发探测各大分发渠道，比对本地记录的各渠道版本与下载直链。一旦发现版本严格递增或检测到同版本静默换包，即刻压入待处理任务列表。
2. 跨市场静默下载与协议适配
   下载引擎根据目标渠道域名自动匹配合规请求头（如强制 IPv4 解析、Android 原生下载器 UA、特定防盗链 Referer 等），规避反爬防火墙的域名劫持与连接重置，获取无损安装包。
3. 容器穿透解包与元数据抽取
   对下载的产物执行格式自适应解包（支持 `.apk`、`.exe`、`.dmg`、`.deb`、`.rpm` 等各类格式）。调用 AAPT 工具或底层字节码扫描器，解析提取完整的应用版本号、构建批次号（Build No）及手机/平板端 SubID。
4. 数据库事务落盘与字典编译
   将提取出的版本实体以原子写入形式追加到原始数据库 `data/qq_subid_map.json`。随后自动唤起运行时编译器，将全量映射编译为轻量级运行时字典 `data/subid.json`，并持久化各渠道的水位线记录文件。
5. 反编译与容错处理（仅官方 Android 主包）
   若检测到更新来自于 Telegram 官方直链，工作流自动联动触发反编译流水线。提取 APK 中的全部 `classes*.dex`，运行 JADX 反编译为 Java 源码，配置局部包名过滤并提供退出码兼容机制。
6. 智能源码 Diff 与补丁打包
   通过 GitHub CLI 自动拉取上一版本的 Release 产物包解压，通过哈希与集合比对过滤混淆干扰，仅对同名实质修改的类执行行级差异提取，生成 Unified Diff 补丁并压缩打包。
7. 资产发布与接力唤醒
   创建 Release 并发布源码包、Diff 补丁及 SubID 元数据说明。若任务队列中仍有待处理版本，自动调用 GitHub API 触发自身工作流执行下一轮处理。

## 模块架构说明

工程核心脚本解耦为模块化微通道架构（位于 `scripts/` 目录）：

```text
scripts/
├── channels/                    # 渠道探测插件目录
│   ├── __init__.py              # 通道统一调度注册表
│   ├── telegram.py              # Telegram 官方更新监控
│   ├── xiaomi.py                # 小米应用商店 (APM 私有签名与下载调度)
│   ├── oppo.py                  # OPPO 软件商店 (动态双 Salt 逆向与 302 换取)
│   ├── huawei.py                # 华为应用市场 (HiSpace 客户端报文协议)
│   ├── vivo.py                  # vivo 应用商店 (Package 结构化开放接口)
│   ├── honor.py                 # 荣耀应用市场 (HmacSHA256 签名体系)
│   ├── samsung.py               # 三星应用商店 (Galaxy Store ODC XML 协议)
│   ├── yingyongbao.py           # 腾讯应用宝 (微下载与固定 CDN 解析)
│   └── wandoujia.py             # 豌豆荚 (PP助手详情与直链)
├── extractor.py                 # 跨市场通用下载、日期校验、AAPT 解包提取工具
├── subid_compiler.py            # 运行时字典编译器 (方案 A 规范)
├── build_subid_database.py      # 历史全量回溯与自愈流水线
├── audit_database.py            # 数据库单调性与异常离群点深度审计工具
└── daily_monitor.py             # 每日增量监听与多通道调度总线入口
```

## 配置与部署

如需在个人仓库中运行此项目，请按以下步骤配置：

### 1. 开启工作流写入权限
工作流需要自动提交版本记录、发布 Release 并支持自动触发后续任务，必须为 `GITHUB_TOKEN` 授予写入权限：
1. 打开 GitHub 仓库，进入 **Settings**。
2. 在左侧菜单中进入 **Actions** -> **General**。
3. 滚动到底部找到 **Workflow permissions**，选择 **Read and write permissions**。
4. 勾选下方 **Allow GitHub Actions to create and approve pull requests**，点击 **Save** 保存。

### 2. 运行工作流
- 定时自动检测（`daily_qq_monitor.yml`）：默认每天自动运行检测。轮询全网八大渠道，提取 SubID 自动入库并推送到主分支；若检测到官方 Android 正式版更新，自动唤醒反编译流水线。
- 手动单包快速录入（`test-extract-appid.yml`）：支持手动输入任意渠道的安装包下载链接和版本号，自动解包分析 SubID，完成数据库写入与推送。
- 手动按需反编译（`decompile.yml`）：
  - `decompile_all`：是否完整反编译整个 APK。
  - `decompile_mobileqq`：局部反编译时是否包含 `com.tencent.mobileqq`。
  - `decompile_qqnt`：局部反编译时是否包含 `com.tencent.qqnt`。

## 性能与架构说明

### 版本与直链双重联合感知设计
传统爬虫单靠版本号字段检测更新，在面对大厂“悄悄换包”（版本号保持不变，但包内代码及 SubID 变更）时会彻底漏报；而单纯依赖 URL 变动，又会因厂商临时回滚旧版本触发重复无效下载。
本项目引入复合判定：
1. 线上版本号严格递增时，正常判定为新版本；
2. 线上版本号与本地记录一致，但下载直链发生变更时，判定为同版本静默换包并触发收录；
3. 线上版本号落后于本地最高水位线时，判定为渠道撤包回滚，自动跳过。
兼顾了数据收录的时效性与历史单调性。

### 针对反编译场景的 Diff 优化
在面对十万级混淆 Java 源码时，传统的 `git diff --no-index` 会因为混淆导致的类名变化触发代价极高的重命名相似度匹配（时间复杂度高达 O(N*M)），导致 CPU 卡死，并生成动辄数 GB、充斥垃圾数据的无意义补丁。
本项目通过 Python 预筛选：
1. 先比对文件路径集合，确定增删文件；
2. 对同名文件优先比对文件尺寸，尺寸一致再计算 MD5；
3. 仅对同名且内容发生变化的类执行行级差异生成。
全流程在 1 分钟内即可完成数十万文件的比对，产出的补丁体积通常仅数兆字节，且具备实际可读性。

### 自适应虚拟内存设计
GitHub Actions 分配给各运行环境的物理机器规格存在随机性（部分为 150GB 单盘机，部分为根目录 30GB、临时目录 70GB 的分盘机）。硬编码 Swap 大小容易在分盘机上触发磁盘耗尽。
自适应算法根据当前物理盘容量动态伸缩，确保在单盘大盘机上跑满 64GB 虚拟内存以提高反编译吞吐量，在小盘或分盘机上收缩至安全阈值，兼顾性能与运行稳定性。
